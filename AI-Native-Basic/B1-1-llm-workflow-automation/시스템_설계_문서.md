# 시스템 설계 문서

## 1. 문제 정의

**업무 과업**: 디자인 리뷰 미팅 요약

**타겟 사용자**: 디자인 리뷰에 참석한 프로덕트 디자이너 본인 (회의 직후 셀프 정리용)

**입력 데이터 형태**: 가상의 회의 녹음 스크립트(텍스트)

**출력 규격**: 아래 8항목
1. 회의 날짜 / 리뷰 차수
2. 참석자
3. 리뷰 대상 (어떤 화면/시안)
4. 전체 디자인 상태 (승인 / 부분 수정 필요 / 재작업 필요)
5. 피드백별 반영 여부 (반영 확정 / 반려 / 추가 논의 필요)
6. Action Items (담당자·기한)
7. 이견 / 미합의 지점
8. 다음 리뷰 일정

**입력 템플릿**:
```
[회의 유형] 디자인 리뷰
[리뷰 차수]
[리뷰 대상 화면]
[참석자]
[스크립트/메모 원문]
[특이사항] (선택)
```

## 2. 페르소나 정의

|---|---|
| 이름 | 정하윤 |
| 역할/직무 | 디자인 리뷰 회의록 정리 담당자 (5년 차 프로덕트 디자이너 출신, 현 디자인 오퍼레이션 담당) |
| 전문 분야 | 디자인 리뷰 프로세스, UI/UX 피드백 정리, 실무 문서 표준화 |
| 말투 | 존댓말, 간결체. 인사말·감탄사·이모지 없음 |
| 금지 사항 | ① 스크립트에 없는 담당자·기한을 지어내지 않는다 ② 화자 불분명 발언을 특정 인물로 단정하지 않는다 ③ 8항목 순서·구성을 임의로 바꾸지 않는다 ④ 과도한 격식 표현을 쓰지 않는다 |
| 우선순위 | 정확성 > 완결성 — 빈칸이 남더라도 틀린 내용을 채우지 않는다 |

## 3. 시스템 프롬프트 (최종 v2)

```
당신은 정하윤입니다. 5년 차 프로덕트 디자이너 출신으로, 현재는 디자인 오퍼레이션 담당자로서 
팀 내 디자인 리뷰 회의록 정리를 전담하고 있습니다.

[목표]
사용자가 제공하는 디자인 리뷰 회의 스크립트를 읽고, 아래 8항목 형식으로 정확하게 요약하는 것이 
당신의 유일한 업무입니다.

[전문성 반영]
디자인 실무 용어(터치 영역, 스테퍼, 반응형, 인터랙션 등)는 풀어서 설명하지 말고 그대로 사용하십시오.

[처리 순서 - 반드시 이 순서를 내부적으로 따르십시오]
1단계. 입력 확인: 참석자, 리뷰 대상, 스크립트 원문이 모두 존재하는지 먼저 점검하십시오.
   → 핵심 정보(참석자, 리뷰 대상)가 통째로 비어있다면, 8항목을 채우지 말고 무엇이 
     부족한지 최대 3개까지 질문한 뒤 답변을 기다리십시오.
2단계. 발언 분류: 스크립트의 각 발언을 다음 중 하나로 분류하십시오.
   - 결론이 난 피드백 (담당자가 반영을 확답했거나 참석자 다수가 동의)
   - 결론이 안 난 피드백 (제안만 되고 확답이나 동의가 없음)
   - 발화자 불분명 구간
3단계. 항목 작성: 2단계 분류를 바탕으로 8항목을 작성하십시오. 이때 결론이 난 것만 
   "반영 확정"으로, 나머지는 "추가 논의 필요"로 분류하십시오.
4단계. 자체 검증: 작성한 내용 중 스크립트에 없는 담당자·기한·날짜를 채운 곳이 없는지 
   다시 확인하고, 있다면 "미정"으로 수정하십시오.

[출력 형식]
반드시 아래 8개 항목을 순서대로, 빠짐없이 작성하십시오.
1. 회의 날짜 / 리뷰 차수
2. 참석자
3. 리뷰 대상 (어떤 화면/시안)
4. 전체 디자인 상태 (승인 / 부분 수정 필요 / 재작업 필요 중 선택)
5. 피드백별 반영 여부 (반영 확정 / 반려 / 추가 논의 필요로 각각 구분)
6. Action Items (담당자, 기한 포함)
7. 이견 / 미합의 지점
8. 다음 리뷰 일정

내부적으로 위 4단계를 거치되, 최종 답변에는 단계별 사고 과정을 노출하지 말고 
8항목 결과만 제시하십시오. 인사말이나 부연 설명도 포함하지 마십시오.
각 반영 여부 판단 뒤에는 근거가 된 스크립트 원문을 짧게 인용해 검증 가능하게 남기십시오.

[안전장치 - 모르면 모른다고 말하기]
스크립트에 명시되지 않은 정보(날짜, 담당자, 기한 등)는 절대 추정해서 채우지 마십시오. 
"미정" 또는 "스크립트에 명시되지 않음"이라고 표시하십시오.
발언자가 불분명한 구간은 특정 인물로 단정하지 말고 "화자 불명"으로 표시하십시오.

[금지 사항]
- 스크립트에 없는 담당자·기한을 그럴듯하게 지어내지 않는다.
- 화자가 불분명한 발언을 특정 인물의 것으로 단정하지 않는다.
- 8항목의 순서나 구성을 임의로 바꾸지 않는다.
- 감탄사, 이모지, 과도한 격식 표현을 쓰지 않는다.
- 핵심 정보가 없는데도 확인 질문 없이 임의로 8항목을 채우지 않는다.
```

## 4. Few-shot 예시 (3개)

### 예시 1. 정상 케이스 (정보 충분)

**입력**: 상품 상세 페이지 리뷰 섹션 UI, 참석자 2인, 승인으로 결론난 1차 리뷰 스크립트

**출력**:
```
1. 회의 날짜 / 리뷰 차수: 스크립트에 명시되지 않음 / 1차 리뷰
2. 참석자: 김하늘(발표자), 박준서(디자인 리드)
3. 리뷰 대상: 상품 상세 페이지 - 리뷰 섹션 UI (v1 시안)
4. 전체 디자인 상태: 승인 (박준서: "전체적으로 승인이에요.")
5. 피드백별 반영 여부: 사진 리뷰 썸네일 60px→80px 확대 — 반영 확정
6. Action Items: 썸네일 크기 80px 수정 — 담당자: 김하늘 — 기한: 다음 주 화요일
7. 이견 / 미합의 지점: 없음
8. 다음 리뷰 일정: 다음 주 화요일 (최종 확인)
```
학습 포인트: 정보가 충분할 때 8항목이 막힘없이 채워지는 기준선을 보여줌.

### 예시 2. 까다로운 케이스 (화자 불명 + 미합의 혼재)

**입력**: 메인 스크립트(장바구니 v2 시안, 2차 리뷰) — 화자 불명 구간, 결론 안 난 쿠폰 정책, 담당자·기한 미명시가 혼재

**출력**: (본 문서 5번 실행 로그 참고 — Claude Sonnet 5 v1 1차 실행 결과와 동일)

학습 포인트: 일부는 명확하고 일부는 애매한 실제 회의에서, 확정/미정/추가논의를 구분하는 기준을 보여줌.

### 예시 3. 모호한 입력 케이스 (핵심 정보 부재)

**입력**:
```
[회의 유형] 디자인 리뷰
[리뷰 차수]
[리뷰 대상 화면]
[참석자]
[스크립트/메모 원문]
오늘 리뷰했는데 스테퍼 크기 늘리기로 했고 쿠폰 쪽은 좀 더 봐야 할 듯. 버튼 위치도 바꾸기로 함.
[특이사항] 없음
```

**출력**:
```
아래 정보가 부족해서 8항목을 정확히 채울 수 없습니다. 확인 부탁드립니다.
1. 참석자가 비어있습니다 — 누가 이 리뷰에 참여했나요?
2. "스테퍼 크기 늘리기로 했다"고 하셨는데, 구체적으로 몇 px에서 몇 px로 변경하기로 했나요?
3. 리뷰 대상 화면이 명시되지 않았습니다 — 어떤 화면/시안을 리뷰하신 건가요?
위 내용을 알려주시면 8항목 형식으로 정리해드리겠습니다.
```
학습 포인트: 미정 처리조차 불가능할 정도로 골격 정보가 없을 땐, 채우지 말고 되물어야 하는 임계점을 보여줌.

## 5. 환각 검증 설계

검증 문항 5개(상세 내용은 `환각_검증_5문항.md` 참고):
1. Action Item 담당자 창작 여부
2. 화자 불명 구간의 발화자 단정 여부
3. 결론 여부 판단 (쿠폰 중복 적용 정책)
4. 다음 리뷰 일정 창작 여부
5. 참석자 범위를 벗어난 정보 요청

**검증 결과**: 5문항 전원 Pass. v2 시스템 프롬프트의 안전장치가 실제로 작동함을 확인.

## 6. 개선 이력 (v1 → v2)

| 항목 | v1 | v2 |
|---|---|---|
| 처리 순서 | 없음 (규칙만 나열) | 4단계 순서 명시 (확인→분류→작성→검증) |
| 판단 흔들림 대응 | 규칙만 제시, 판단 기준은 모델 자율 | "결론 난 것"의 정의를 구체화(확답/다수 동의) |
| 모호한 입력 대응 | 없음 | 1단계에 핵심 정보 부재 시 질문하는 로직 추가 |
| 출력 노출 제어 | 없음 | 추론 과정 비노출 규칙 명시 |

**개선 검증 결과**: 동일 스크립트를 v1·v2 각각 2회씩 실행한 결과, v1은 애니메이션 반영 여부 분류와 Action Item 담당자 표기 방식이 실행마다 흔들렸으나, v2는 두 지점 모두 2회 실행에서 일관된 결과를 보였다. v1→v2 개선이 실제로 재현성을 높였음을 확인.

## 7. 비용 절감 및 무료 모델 대체 전략

### 무료 모델 대체 전략
유료 3종(GPT-5.6, Gemini 3.1 Pro, Claude Sonnet 5) 비교를 기준으로 삼되, 예산 제약 시 아래 무료 티어로 대체 가능하다.

| 유료 모델 | 무료 대체 모델 | 제약 |
|---|---|---|
| GPT-5.6 (Thinking) | GPT-5.6 Instant (무료 티어) | 추론 깊이가 얕아 애매한 반영여부 판단(예: 애니메이션 건) 정확도 하락 가능 |
| Gemini 3.1 Pro | Gemini 3.7 Flash (무료 티어) | 장문 스크립트에서 형식 누락 위험 소폭 증가 |
| Claude Sonnet 5 | Claude 무료 티어 (메시지 수 제한) | 하루 처리 가능 회의록 건수가 제한됨 (일일 한도 도달 시 익일까지 대기) |

무료 티어 사용 시, 반드시 환각 검증 5문항을 재실행하여 Pass 여부를 확인한 뒤 실무에 투입해야 한다. 무료 모델은 동일 프롬프트에서도 유료 모델보다 판단 흔들림(일관성 저하) 가능성이 높기 때문이다.

### 프롬프트 경량화
현재 v2 시스템 프롬프트는 처리 순서 4단계, 금지 사항 5개, Few-shot 예시 3개(약 1,500자 이상)를 포함해 토큰 소모가 크다. 비용 절감이 필요할 경우 아래 순서로 경량화한다.

1. **1차 축소**: Few-shot 예시 3개 중 2번(까다로운 케이스)만 유지하고 1번(정상 케이스)·3번(모호한 입력)은 제거한다. 정상 케이스는 규칙만으로도 처리 가능하고, 모호한 입력 대응은 [처리 순서] 1단계 규칙만으로 충분히 유도되기 때문이다.
2. **2차 축소**: [처리 순서] 4단계 설명을 각 1문장으로 압축한다 (예: "부재 정보 확인 → 발언 분류 → 항목 작성 → 자체 검증 순으로 진행").
3. **경량화 한계선**: [안전장치]와 [금지 사항] 섹션은 축소하지 않는다. 이 두 섹션이 환각 검증 통과의 핵심 근거이므로, 여기를 줄이면 비용은 아끼지만 검증을 다시 통과하지 못할 위험이 크다.

### 후처리 비용 절감 체크리스트
- [ ] 8항목 존재 여부는 모델 재호출 없이 정규식(각 항목 번호 패턴 매칭)으로 1차 검증하고, 누락 시에만 모델에 재요청한다.
- [ ] 하루 여러 건의 회의록을 처리할 경우, 개별 요청 대신 배치로 묶어 한 번의 호출에 여러 스크립트를 순차 처리하도록 요청해 호출 수를 줄인다.
- [ ] 근거 인용(원문 발췌) 규칙은 유지하되, 인용 길이를 "1문장 이내"로 제한해 출력 토큰을 줄인다.
- [ ] 이미 처리한 스크립트와 동일한 스크립트가 재입력되는 경우(중복 요청)를 걸러내는 절차를 마련한다.

## 8. 정책 변경 시 운영 전략 (롤아웃/롤백/검증 파이프라인)

### 배포 흐름
```
[변경 제안] → [샌드박스 테스트] → [검증 파이프라인 통과] → [파일럿 적용] → [전체 롤아웃]
                                        ↓ (실패 시)
                                   [롤백: 직전 버전으로 즉시 복귀]
```

### 검증 파이프라인 (신규 버전 배포 전 필수 통과 기준)
새 버전(예: v3)을 실제 배포하기 전, 아래 3단계를 순서대로 통과해야 한다. 하나라도 실패하면 배포를 보류하고 직전 버전을 유지한다.

1. **환각 검증**: 본 문서 5번의 5문항을 재실행하여 전원 Pass 확인
2. **일관성 검증**: 동일 스크립트를 2회 이상 재실행하여 반영여부 분류·담당자 처리 방식이 흔들리지 않는지 확인 (v1→v2 개선 시 사용한 방법과 동일)
3. **회귀 검증**: 이전 버전에서 이미 통과했던 Few-shot 예시 3개를 새 버전에 그대로 입력해, 기존에 잘 처리하던 케이스가 새 버전에서 오히려 나빠지지 않았는지 확인

### 롤아웃 절차
1. **파일럿 적용**: 새 버전을 1주일 또는 5건의 실제 회의록에 한해 시범 적용
2. **비교**: 같은 기간 직전 버전으로 처리했다면 어땠을지 표본 2~3건을 직접 비교
3. **전체 적용**: 파일럿에서 문제가 없으면 전체 적용, 문제 발견 시 롤백

### 롤백 절차
1. 문제 발견 즉시 직전 버전 시스템 프롬프트 파일로 교체한다 (버전별 파일을 항상 별도 보관하므로 즉시 교체 가능)
2. 롤백 사유와 발견된 문제를 버전 이력에 기록한다 (아래 버전 관리 표 참고)
3. 문제를 수정한 재발 방지 버전을 만들어 다시 검증 파이프라인을 통과시킨 뒤에만 재배포한다

### 버전 관리 절차
- 시스템 프롬프트는 버전마다 별도 파일로 저장한다 (예: `system_prompt_v1.md`, `system_prompt_v2.md`). 덮어쓰지 않는다.
- 변경 이력은 아래와 같이 표로 관리하며, 배포일과 검증 결과를 함께 기록한다.

| 버전 | 변경 내용 | 검증 파이프라인 결과 | 배포일 | 상태 |
|---|---|---|---|---|
| v1 | 최초 페르소나·규칙 기반 프롬프트 | 일관성 검증 실패 (반영여부·담당자 흔들림) | - | 폐기 |
| v2 | 4단계 처리 순서 추가 | 환각검증 5/5 Pass, 일관성 검증 2회 안정 | 2026-08-15 | 사용 중 |
| v3 (예정) | 경량화 버전 (본 문서 7번 적용) | 미검증 | - | 검증 대기 |

## 9. 문맥 유지 개선 방안 (세션 관리·체크포인트·프롬프트 청크화)

10턴 대화 로그 검증에서는 문맥 유지가 안정적으로 확인됐으나, 이는 10턴 규모 기준이다. 실무에서 하루 여러 건의 회의록을 한 세션에서 연속 처리하거나, 회의 자체가 1시간 이상으로 길어질 경우를 대비한 구체적 방안은 다음과 같다.

### 세션 관리 원칙
- **회의 단위로 세션을 분리한다.** 서로 다른 회의(예: 3차 리뷰와 4차 리뷰)를 같은 세션에서 계속 이어 처리하면, 이전 회의의 참석자·용어가 다음 회의 요약에 섞여 들어갈 위험이 있다. 회의가 바뀌면 새 세션(새 대화)을 시작하는 것을 기본 원칙으로 한다.
- 부득이하게 한 세션에서 여러 회의를 연달아 처리해야 할 경우, 매 회의 스크립트 제출 시 "이전 회의와 무관한 새 리뷰입니다"라는 문구를 함께 명시해 모델이 이전 맥락과 분리해 처리하도록 유도한다.

### 요약 체크포인트 (세션이 길어질 때)
10턴을 넘어 대화가 길어질 경우, 매 5~7턴마다 아래와 같은 체크포인트 요약을 요청해 문맥을 앵커링한다 (10턴 로그의 마지막 턴에서 사용한 방식을 정례화한 것).

```
체크포인트 요청 예시: "지금까지 유지한 규칙과, 중간에 변경된 조건을 각각 정리해줘"
```

이 체크포인트 응답을 대화 중간중간 명시적으로 받아두면, 이후 턴에서 규칙이 흐려지더라도 직전 체크포인트를 참조해 바로잡을 수 있다.

### 프롬프트 청크화 (긴 회의록 처리)
1시간 이상의 긴 회의 스크립트를 한 번에 입력하면 뒷부분 내용이 상대적으로 소홀히 처리될 위험이 있다. 이 경우:

1. 스크립트를 15~20분 단위(또는 주제 전환 지점 기준)로 나눈다.
2. 각 청크를 순서대로 입력하되, "이것은 전체 회의의 N번째 구간입니다. 이전 구간 요약을 이어받아 계속 진행하세요"라고 명시한다.
3. 마지막 청크 처리 후 "전체 구간을 종합해 8항목 최종본을 작성해달라"고 요청해 병합한다.

이 절차는 아직 실제 검증하지 않았으며, 향후 긴 회의록 샘플로 별도 검증이 필요하다.

## 10. 설계 시 고려사항 (실무 적용 시 주의)

- 본 설계는 시스템 프롬프트 내 규칙("각 반영 여부 판단 뒤 스크립트 원문을 인용")을 포함하고 있다. 이번 과제는 가상 인물로 구성된 스크립트라 실명 인용에 문제가 없으나, 실제 회의록에 이 시스템을 적용할 경우 발언자 실명이 그대로 노출된 인용문이 문서에 남는다는 점을 고려해야 한다. 필요 시 "발언자를 역할명으로 치환하여 인용"하도록 규칙을 추가하는 것을 권장한다.
- 화자 분리(음성→텍스트 변환 시 발화자 구분)의 정확도는 이 시스템의 입력 단계 이전, 즉 STT 도구의 성능에 좌우된다. 본 시스템은 이미 텍스트로 변환된 스크립트만 처리하므로, 화자 오분리 자체를 교정할 수는 없다. 다만 스크립트에 "화자 불명"으로 명시된 구간을 근거 없이 특정 인물로 확정하지 않도록 설계했다.
